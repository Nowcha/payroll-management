# 給与明細ベース 還付金試算ツール 要件定義書

Oct 15, 2026 · @Nowcha

## 1. 目的・スコープ・前提

毎月の給与明細を起点に、年の途中から「年末調整後の過不足」「確定申告での還付額」「ふるさと納税の残枠」を常に見通せる個人用ツールを作る。申告書の作成・提出は既存のマイナポータル連携とe-Taxに任せ、本ツールは年中の試算と管理に特化する。

**対象**

- 利用者：本人（夫）1名で、年末調整を受ける給与所得者。配偶者は共働きで控除の対象外。家族は医療費の受診者として、子は生命保険料控除の23歳未満特例の判定用としても管理する
- 対象年分：給与明細は令和6年分（2024年）から登録する。税計算は2024〜2026年分に対応し、以降は年分ごとに税制パラメータを追加する。2024・2025年分は源泉徴収票との突合で計算エンジンを検証する。医療費などを入れれば、還付申告（翌年から5年間可能）の要否確認にも使える
- 対象税目：所得税（復興特別所得税含む）と、ふるさと納税上限の算定に必要な範囲の住民税

**非スコープ**

- 確定申告書の作成・e-Tax送信
- 事業所得・雑所得（副業）、不動産所得、株式・配当の申告（特定口座・源泉徴収ありで申告不要を前提）
- 勤務先の給与計算そのものの再現（月々の源泉徴収税額は明細の実績値を使う）

**前提・制約**

- APIキーを使わない（外部AI APIやOCR APIは呼ばない）
- 給与・医療・家族のデータは端末外に送信しない
- 試算値は目安であり、最終判断は源泉徴収票と申告書作成コーナーの計算結果で行う

## 3. 計算ロジック

年税額を「年末調整ベース」と「確定申告ベース」の2回計算し、差を還付見込みとする。両者の違いは、年末調整では医療費控除と寄附金控除を入れられない点だけに集約される。

### 3.1 予測

- 既定の方式：毎月固定の項目（基本給、社会保険料、住民税）は直近月の値を延長。変動項目（時間外手当など）は直近3か月平均。賞与は前年同月実績
- 住民税は6月で年度が切り替わるため、6月以降は新年度額で予測する
- 源泉所得税の予測は直近3か月の「課税支給額に対する源泉税率」を予測支給額に掛けて求める。ただし12月は年末調整の精算を含むので、「年調ベースの年税額 − 1〜11月の源泉徴収税額の合計」で予測する
- 令和8年分の基礎控除・給与所得控除の引上げは月々の源泉徴収に反映されず、12月の年末調整でまとめて精算される。予測ロジックはこれを前提に、12月の年調精算額を別建てで見込む

令和6年分は定額減税で、6〜12月の源泉所得税と住民税（6月は0円、7月以降に11回払い）が通常と異なる。この期間は比較画面で「特殊要因あり」と注記し、2025年分を予測するときの「前年同月実績」からは除外して、直近平均に切り替える。

### 3.2 所得税（年末調整ベース）

1. 給与収入 ＝ 課税支給の年合計（実績＋予測、非課税の通勤手当等は除く）
2. 給与所得 ＝ 給与収入 − 給与所得控除
3. 所得控除 ＝ 社会保険料 ＋ 生命保険料 ＋ 地震保険料 ＋ 小規模企業共済等掛金 ＋ 配偶者・扶養 ＋ 基礎
4. 課税所得 ＝ 給与所得 − 所得控除（1,000円未満切捨て）
5. 算出税額 ＝ 課税所得 × 税率 − 速算控除額
6. 年税額 ＝（算出税額 − 住宅ローン控除 − 定額減税〔2024年分のみ〕）× 102.1%（100円未満切捨て）
7. 年末調整の過不足 ＝ 年税額 − 1〜12月の源泉徴収税額の合計（プラスなら追加徴収、マイナスなら還付）

### 3.3 確定申告での還付

3.2の所得控除に医療費控除と寄附金控除を加えて年税額を再計算し、年末調整ベースとの差を還付見込みとする。

```latex
\text{還付見込み} = \text{年税額}_{\text{年調}} - \text{年税額}_{\text{申告}}
```

- 寄附金控除（所得税）＝ 寄付合計 − 2,000円（総所得金額等の40%が上限）
- 確定申告をするとワンストップ特例は無効になる。医療費控除で申告する年は、ふるさと納税の全寄付を申告に含める前提で計算し、画面でも警告する

### 3.4 医療費控除

```latex
\text{医療費控除} = \min\left( (\text{支払医療費} - \text{補填額}) - \min(100000,\ \text{総所得金額等} \times 5\%),\ 2000000 \right)
```

- 補填額は支出ごとに紐づけて差し引く（一時金が特定の出産費用を上回っても、他の医療費からは引かない）
- セルフメディケーション税制（対象医薬品の購入額 − 12,000円、上限88,000円）と比較し、有利な方を表示する。併用はできない

### 3.5 ふるさと納税の上限

```latex
\text{上限額} = \frac{\text{住民税所得割額} \times 20\%}{90\% - \text{所得税の限界税率} \times 1.021} + 2000
```

- 住民税所得割額 ＝（総所得金額等 − 住民税の所得控除）× 10% − 調整控除 − 住宅ローン控除の住民税分
- 住民税の所得控除は所得税と金額が異なる（基礎控除、生命保険料控除の上限など）。4章の住民税パラメータを使う
- 式の「所得税の限界税率」は、住民税の課税総所得金額から人的控除差調整額を差し引いた金額で判定する（[総務省](https://www.soumu.go.jp/main_sosiki/jichi_zeisei/czaisei/czaisei_seido/furusato/mechanism/deduction.html)）
- 医療費控除を使うと所得割額が下がり上限も下がるため、医療費控除ありの上限を併記する
- 安全側に寄せるため、予測を含む間は上限の90%を「推奨寄付額」として表示する

## 5. データモデル

明細は「ヘッダ＋明細行」の2層で持ち、税計算はすべて項目マスタの分類タグ経由で集計する。項目名が会社や年で変わっても計算ロジックに影響させないためである。金額はすべて円単位の整数で保持する。

| エンティティ | 主な属性 | 備考 |
| --- | --- | --- |
| Payslip（明細ヘッダ） | id、年分、対象月、種別（給与／賞与）、支給日、状態（実績／予測）、明細記載の累計（支給・社会保険・所得税）、勤怠時間、取込元ファイル名 | 予測明細は実績登録時に削除・置換 |
| PayslipLine（明細行） | payslipId、itemId、金額、予測方式（予測時のみ） | 1明細に複数行 |

## 6. 非機能要件・技術構成

構成はReact＋Vite＋TypeScript＋Tailwind CSSの静的サイトをGitHub Pagesで配信し、データはブラウザ内のIndexedDBだけに置く。サーバーもAPIキーも持たないので、運用コストと漏えい経路の両方がゼロになる。

| 観点 | 要件 |
| --- | --- |
| データ保管 | IndexedDB（Dexie.js）に保存。外部送信なし。リポジトリにはコードと税制パラメータのみ置く |
| バックアップ | 全データをJSONでエクスポート／インポート。パスフレーズによるAES-GCM暗号化（Web Crypto API）を選択可能 |
| 端末 | PWAとしてPC・iPhoneのホーム画面から起動、オフライン動作。スマホ幅（380px）でも全画面が使えること |
| 計算の正確性 | 計算エンジンはUIから独立した純粋関数のTSモジュールにし、Vitestで単体テスト。国税庁の計算例と前年の源泉徴収票を検証ケースにする |
| 端数処理 | 課税所得は1,000円未満、年税額は100円未満の切捨てなど、法定の端数処理をパラメータとして保持 |
| 説明可能性 | すべての試算結果に「どの値（実績・予測・登録値）から、どの式で」出たかを段階表示 |
| 明細取込 | アプリ内でpdf.jsによりPDFのテキストを抽出し、会社別のレイアウト定義（JSON）で項目に割り当てる。APIは呼ばない。「総支給 − 控除合計 ＝ 差引支給額」の検算を通らない明細は登録しない |
| 開発環境 | Windows 11／PowerShellで完結（WSL不要）。GitHub Actionsでビルドとテストを実行してPagesにデプロイ |

### 6.1 PDF取込の方式とAIモデルの使い分け

PDFは毎月AIに読ませず、AIで一度レイアウト定義（パーサー）を作り、以降は決定的に処理する。全件をAIで読む方式より、誤読が起きず、給与データがモデルに渡るのもサンプル数枚に限られ、使用量も小さい。

AIはClaude Code（Proサブスクリプション内）で使い、作業ごとに下表のモデルに固定する。切替はセッション中の`/model`で行い、繰り返す作業はサブエージェント定義の`model`欄で固定する（例：`.claude/agents/payslip-pdf-reader.md`に`model: sonnet`）。

| 作業 | モデル | effort | 理由 |
| --- | --- | --- | --- |
| 要件・設計、税計算エンジンの実装とテスト | Opus 5.5 | high | 金額の正確性が最重要。Proの既定モデル |
| PDF様式の解析と読取ルールの作成（2024年1月分で実施済み。様式が変わったときだけ再実施） | Opus 5.5 | high | 一度の誤りが全月に波及するため最上位で作る |
| 税制パラメータの一次資料突合 | Opus 5.5 | medium | Web検索で根拠URLを記録するだけの定型作業 |
| 画面・CRUD・グラフなどの実装 | `opusplan`（計画はOpus 5.5、実装はSonnet 5.5） | medium | 定型実装は速度と使用量を優先 |
| レイアウト定義で読めないPDFの個別抽出（スキャン画像など） | Sonnet 5.5（サブエージェント） | medium | 画像の数値読取に十分な精度。結果は検算で機械チェック |
| PDFの仕分け（給与／賞与／年末調整／源泉徴収票の判別、ファイル名整理） | Haiku 5.5（サブエージェント） | low | 種別判別のみで、金額は読ませない |

Fable 5.1は使わない。プランによっては使用量クレジットの課金対象になり、サブスクリプション内で完結させる方針に反する。本件の規模ならOpus 5.5で足りる（[Claude Code モデル設定](https://code.claude.com/docs/en/model-config)）。

### 6.2 サンプル明細（2024年1月分）の解析結果

サンプルはテキスト埋め込み型で、項目名と金額の両方を座標付きで取得できた。項目は金額がある月にだけ印字されるため、項目ごとに位置を固定する定義は使わない。「項目名の行の直下、同じ列にある数値をその項目の金額とする」汎用ルールで読む。

- 様式：A4横1ページ。支給・控除・勤怠・記事の4ブロックが、それぞれ9列×（項目名行／金額行）の格子になっている。金額は列内で右寄せ
- 文字コード：日本語はCIDフォント（UniJIS-UCS2-HW-H）。pdf.jsは`cMapUrl`と`cMapPacked: true`を指定すれば読める。未指定だと項目名が空になるので、取込時に「項目名0件」を検知してエラーにする
- 空欄：課税対象額の欄は空欄だった。課税支給額は「支給合計 − 非課税支給 − 社会保険料合計」で計算する
- 累計欄：支給累計・社会保険累計・所得税累計が毎月載る。「前月累計＋当月＝当月累計」の照合で取込漏れの月を検出できる。12月の累計は源泉徴収票（年調前の値）とも突合できる

| 項目名 | ブロック | 税分類 | 備考 |
| --- | --- | --- | --- |
| 基本給 | 支給 | 課税支給 |  |
| 住宅手当 | 支給 | 課税支給 |  |
| 前払退職金 | 支給 | 課税支給 | 給与として課税される |
| 時間外勤務手当 | 支給 | 課税支給 | 予測は直近3か月平均 |
| 健康保険・厚生年金・雇用保険 | 控除 | 社会保険料 |  |
| 社会保険料合計 | 控除 | 小計（集計対象外） | 検算にだけ使う |
| 所得税 | 控除 | 所得税 |  |
| 住民税 | 控除 | 住民税 |  |
| 株式購入 | 控除 | その他控除 | 税計算には影響しない。割引分は別途課税済み |
| 時間外勤務時間・深夜時間・休日時間 | 勤怠 | 対象外（時間数） | 時間外手当の予測に使う |
| 第１口座・銀行振込額 | 記事 | 対象外 | 差引支給額との検算に使う |

検算は次の5本で行い、サンプルは5本とも一致した：支給項目の和＝支給合計、社保3項目の和＝社会保険料合計、控除項目の和（小計を除く）＝控除合計、支給合計 − 控除合計＝差引支給額、差引支給額＝銀行振込額。初めて出てきた項目名（通勤手当、定額減税額、賞与など）では取込を止めず、項目マスタの分類待ちとして表示する。
